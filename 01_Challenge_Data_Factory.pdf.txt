صورت مسئله در یک نگاه 
شهرداری نیویورک تمام شکایتها و درخواست های خدمات شهری خود را بهصورت عمومی و از طریق  API  منتشر  می کند:  هر   
رکورد  یک   تماس  شهروند  است  —  صدای  بلند،  چاله  در  خیابان،  نبود  آب  گرم،   درخت  افتاده  —  با  تاریخ  ثبت،   تاریخ   بسته 
شدن، آژانس مسئول، نوع شکایت، و موقعیت مکانی.  
یک تیم تحلیل می خواهد به این سؤال پاسخ دهد:  در هر محله، شهرداری برای هر نوع شکایت چقدر طول می « کشد تا پرونده
را ببندد، و این عدد دارد بهتر می  »شود یا بدتر؟ 
شما *به این سؤال پاسخ نمی دهید*. کار شما یک قدم عقب تر است و سخت تر:  ساختن کارخانهای که داده  قابلاعتماد  برای  
چنین سؤال هایی  تولید کند.  
داده  خام  این  API  برای  تحلیل   آماده  نیست:  فیلدهای  تاریخ  بهصورت  رشته  می آیند،  کد  پستی  گاهی  00000    یاN/A   یا با
فاصله اضافه است، نام محله گاهی Unspecified  است، بعضی پروندهها تاریخ بستهشدن قبل از تاریخ ثبت دارند، رکوردهای 
تکراری وجود دارد، و API   یکجا همه داده را به شما نمی دهد.  
مسئله  شما  این  است:  از یک منبع زنده  شلخته،  یک  dataset   تمیز،  مستند،  تکرارپذیر  و   قابل  اتکا  بسازید   —  طوری  که   اگر  
فردا دوباره اجرا شود، نه داده  تکراری بسازد و نه داده سالم را دور بریزد.

۱) یک package  واقعی، نه چند فایل اسکریپت 
پروژه باید بهصورت یک  package   قابل نصب و قابل اجرا از خط فرمان در بیاید. یک فرمان، کل کارخانه را از ابتدا تا انتها
می چرخاند؛ همان فرمان با پارامترهای دیگر باید فقط یک بخش را بچرخاند. 
• تنظیمات (بازه زمانی، اندازه دسته، مسیرها، سقف تلاش مجدد) بیرون از کد باشد.  
• هیچ مقدار جادویی (magic value ).داخل منطق نباشد 
• یک سلسله مراتب  Exception    اختصاصی پروژه داشته باشید و کد خروج فرایند ( exit code)   بر اساس نوع خطا 
متفاوت باشد: خطای شبکه، خطای اعتبارسنجی داده، و خطای تنظیمات نباید یک جور دیده شوند. 
۲) دریافت تدریجی، قابل ازسرگیری و idempotent 
• API  همهداده را یک جا نمی دهد؛ دریافت باید دسته ای باشد. 
• اگر فرایند در میانه کار قطع شود، اجرای بعدی باید از جایی که مانده ادامه دهد، نه از صفر.  
• اگر فرایند دو بار کامل اجرا شود، خروجی نهایی نباید یک رکورد تکراری داشته باشد و نباید تغییر کند. 
• رفتار در برابر پاسخ های غیر ۰۰۲ و پاسخ های ناقص/نامعتبر باید تعریف شده باشد، نه تصادفی. 
• لایه  HTTP  باید  هر دو شکل درخواست  GET    وPOST    را پشتیبانی کند، چون منبع بعدی ممکن استGET   .نپذیرد
پشتیبانی از  POST    باید با تست اثبات شود، حتی اگر منبع فعلی به آن نیاز نداشته باشد. در گزارش یک جمله: چرا
یک API   یکی را میپذیرد و دیگری را نه. 
• سقف مصرف حافظه:  در هیچ لحظه ای نباید کل داده  خام  همزمان  در  حافظه  باشد.  این  محدودیت  را  باید  بتوانید   
نشان دهید.  
۳) قرارداد schema و قرنطینه، بهجای دور ریختن بیصدا  
یک  قرارداد صریح  برای  dataset  نهایی  بنویسید:  هر  ستون   چه  نوعی  دارد،  آیا  می تواند  خالی  باشد،  دامنه  مجاز  مقادیرش 
چیست، و چه چیزی آن را یکتا  می کند.  
سپس: 
• هر رکوردی که قرارداد را نقض کند  حذف نمی شود؛ به یک خروجی جداگانه   »قرنطینه«  میرود،  همراه  با   کد دلیل   
مشخص (چرا رد شد). 
• در پایان اجرا، تعداد رکورد در هر کد دلیل گزارش می شود.  
• اگر نسبت قرنطینه از یک آستانه  تعریف شده  (آستانه  را  خودتان  انتخاب  و  توجیه  کنید )  بالاتر  رفت،  اجرا  باید   
شکست بخورد، نه اینکه با داده مشکوک ادامه دهد. 
این بخش قلب چالش است: تفاوت یک کارخانه  داده  با  یک  اسکریپت  پاک سازی،  در  این  است   که  کارخانه  میداند  چه  چیزی  را  
دور انداخته و چرا.

۴) پاکسازی و ترکیب  
روی داده عبورکرده از قرارداد : 
• نوع دادهها را به شکل درست خود برسانید (تاریخ، عدد، دستهای). 
• مقادیر گمشده را تعیین تکلیف کنید. برای هر ستون، سیاست شما باید در گزارش دلیل داشته باشد؛ سیاست 
یکسان برای همه ستون ها بدون توجیه، یک  تصمیم  ضعیف حساب می شود.  
• تکراری ها را تعریف کنید.   در این داده بدیهی نیست»تکراری« :توجه؛ تعریف شما از رکورد تکراری باید نوشته و  
دفاع شود. 
• داده نامعتبرِ منطقی (مثل  پروندهای که قبل از  ثبت بسته شده) را شناسایی و  تعیین تکلیف  کنید.  
• منبع دوم (محله/جمعیت) را به داده  اصلی  متصل  کنید.  تعداد سطرهای قبل و بعد از اتصال باید توضیح داده شود؛ 
اگر اتصال سطر اضافه یا کم کرد، باید بدانید چرا. 
۵) خروجی نهایی  
سه خروجی: 
1 .dataset تحلیلی ، با ستون»پرونده« در سطحهای محاسبه شده لازم برای سؤال تیم تحلیل  (از جمله مدت زمان  تا بسته

2. یک جدول تجمیعی که همان سؤال اصلی را در قالب جدولی قابل ماه. ×  نوع شکایت× خواندن بدهد: منطقه 
• این جدول باید در  قالب عریض (wide)    باشد—  یعنی  چیزی  که  یک  انسان  بتواند  روی  صفحه  بخواند  و  روند  را

3  . یک manifest  اجرا  (run_manifest.json  :)  بازهزمانی  دریافت شده،  تعداد  رکورد  خام،  تعداد  عبورکرده،  تعداد

الزام قطعی بودن (determinism:)    دو اجرای مستقل روی همان بازهزمانی  باید  فایل های  خروجی  با  hash  یکسان  بدهند.  اگر  
نمی دهند، چیزی در کارخانه شما غیرقطعی است و باید پیدایش کنید.

• منطق ازسرگیری: نقطه ادامه درست محاسبه شود.

۱. بازه متحرک: کارخانه باید بتواند با یک پارامتر، فقط داده  از« آخرین اجرا  تا »الان را بگیرد — نه همیشه کل ۸۱ ماه.  
۲. تغییر شکل منبع:   فرض کنید فردا  API    یک ستون را حذف کند یا نوعش را عوض کند. سیستم شما باید این را

نوتبوک، در ادامه کارخانه، باید  یک EDA واقعی روی dataset تمیز داشته باشد:

پیش نمایش مرحله بعد  
خروجی این مرحله در مرحله  ۲  داخل  یک  PostgreSQL   میرود  و  شما  باید  روی  آن  کوئریهایی  بزنید  که  زیر بودجه  زمانی

و یک هشدار معماری که اگر الان جدی بگیرید، دو مرحله بعد برایتان ارزان تمام  می شود:  
همین کارخانه در مراحل بعد باید  منبع های تازه  (از جمله فایل، نه فقط  API  )  ومقصدهای تازه  (از جمله  Database  ) را 
بپذیرد — بدون این که منطق  اعتبارسنجی، قرنطینه و manifest دوباره نوشته شود.  
 
اگر امروز دریافت از  HTTP   و  نوشتن  روی  دیسک  را  در  دل   هم  ببافید،  در   مرحله  ۲  و  ۳  مجبور  به  بازنویسی   می شوید   و   
وقت  آن  مراحل  را  این جا  از  دست  دادهاید.  این که  چطور  این  انعطاف  را  می سازید،  گفته  نمی شود  —  اما  این که  لازمش   
دارید، گفته شده است.
